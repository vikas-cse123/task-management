# ADR 0004 — Better Auth Identity & User Reference Strategy

- **Status:** Accepted
- **Date:** 2026-10-17
- **Context:** Phase 1 must reference users (client team members, designated
  client-role employees, the responsible primary Manager, and audit actors)
  from application-domain collections without creating a duplicate identity
  system. The reference strategy must match how the installed Better Auth
  MongoDB adapter actually stores users.

## Verified facts (from the installed packages)

Inspected versions: **`better-auth@1.7.10`** and
**`@better-auth/mongo-adapter@1.7.10`** (dependency of `apps/api`).

From `@better-auth/mongo-adapter/dist/index.mjs` and the Better Auth core
schema loader:

1. The adapter maps the logical `id` field to the physical `_id` field
   (`mapKeysTransformInput: { id: "_id" }`, `mapKeysTransformOutput: { _id: "id" }`).
2. The default identifier type is **`ObjectId`**. The adapter switches to `UUID`
   only when `advanced.database.generateId === "uuid"` is configured. Hex
   `ObjectId` strings are what the adapter returns as `id`.
3. `usePlural` defaults to **false**, so the default model/collection names are
   **singular**: `user`, `session`, `account`, `verification`.
4. Multi-document transactions are enabled by default when a `MongoClient` is
   supplied to the adapter, and must be explicitly disabled
   (`transaction: false`) on a standalone server.

## Decision

- Application-domain documents reference a user by storing the Better Auth
  user **`ObjectId`** in an `ObjectId` field (`userId`, `actorId`,
  `primaryManagerId`) with `ref` set to the Better Auth model name `user`.
- **No custom user identifier** is generated anywhere in the application.
- Employee attributes needed for assignment validation (existence, active
  status, held job roles) are accessed through an `EmployeeDirectory`
  abstraction (`packages/db/src/services/employee-directory.ts`). This keeps
  identity ownership with Better Auth and avoids duplicating it. The concrete
  database-backed implementation is bound in the authentication step.
- Whether the application profile fields live on the Better Auth `user`
  document (via `additionalFields`) or in a separate `users` profile collection
  is **deferred to the authentication step**. Either way, the identity key is
  the adapter's user `_id`; both options are compatible with this decision. The
  choice is recorded as open item 10 in `docs/decisions.md`.

## Consequences

- References are type-consistent (`ObjectId`) across all Phase 1 collections.
- No Mongoose model is registered for the user collection in this step, so
  `ref: 'user'` is informational; integrity is enforced through
  `EmployeeDirectory`, not `populate`.
- If the authentication step enables `advanced.database.generateId = "uuid"`,
  this decision must be revisited (the reference type would change to `UUID`).
- Indexes on `userId`/`actorId`/`primaryManagerId` remain valid regardless of
  which option is chosen for the profile store.

## Alternatives considered

- **Custom user ID generated by the application** — rejected: duplicates
  identity and contradicts the spec's "avoid unnecessary custom ID generation".
- **Separate identity collection maintained alongside Better Auth** — rejected:
  duplicate identity system (correction F).
